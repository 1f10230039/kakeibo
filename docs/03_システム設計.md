### 1.1 取り込みと API を分ける理由 ✅（10/6）

- Apps Script の簡単な Gmail 機能（GmailApp）は、**メールの閲覧・送信・削除まで全部**の権限（`https://mail.google.com/`）が必要になる（出典：[GmailApp](https://developers.google.com/apps-script/reference/gmail/gmail-app)）。そこで Gmail API を**読み取り専用**（`gmail.readonly`）の権限で使う
- インターネットから呼ばれる API は、Gmail の権限を持たない別の Apps Script にする。万一 API に穴があっても、Gmail には届かない
- 読み取り専用なので、メールにラベル（取り込み済みの印）は付けられない。代わりに、取り込んだメールの番号をシートから引いて二度取り込まないようにする（F-02）

### 1.2 GitHub Pages が公開リポジトリになることについて ✅（10/6）

- リポジトリに置くのは**画面のコードと写真だけ**。家計のデータ、合言葉、スプレッドシートの ID は置かない
- コードが公開されても、合言葉がなければデータは読めないように作る（5章）
- 写真も公開されるので、**写っても困らない写真（風景など）だけ**にする

#### 3.1.1 速報のうちの支払月 ✅（10/6 公式で確認）

楽天カードの締め日は**毎月末日**、引き落としは**翌月27日**（土日祝日なら翌営業日）。ただし**楽天市場・楽天ペイ・楽天トラベルの利用分だけは25日締め**。出典：[楽天カード「みんなのマネ活」](https://www.rakuten-card.co.jp/minna-money/credit-card/select/article_2108_00001/)

速報版には利用先が書いていないので、楽天市場などかどうかは区別できない。そこで、速報のうちは **利用日の翌月** を仮の支払月にして、確定版が来たらメールに書いてある支払月で書き換える。楽天市場などで26日〜月末に使った分だけは、速報のあいだ仮の支払月が1か月ずれる。

#### 3.1.2 ポイント払い（10/7）

楽天カードの「ポイントで支払いサービス」（楽天カードアプリ・e-NAVI）で、カードの請求をポイントで払った記録。本人が S-07 で手で入れる（addPointPayment）。

- 公式ページで確かめたこと（10/7）：毎月12日（請求確定金額反映後）〜最長24日に手続きでき、**当月請求分**（その月の27日の引き落とし）から 1ポイント＝1円で引かれる。50ポイントから・通常ポイントだけ・手続きのあと取り消しはできない。ポイントの履歴は楽天PointClub に「ポイントで支払いサービスでポイント利用」と出る。手続き完了のメールは公式ページに記載なし（本人の Gmail でも見つからなかった）。e-NAVI の利用明細の CSV にも出てこない（2〜10月払いの9つで確認）
- 行：種類＝収入・名前（メモ）＝ポイント・状態＝ポイント払い・出どころ＝手入力・支払月＝使った日の月・カテゴリなし
- 数え方（本人の決定）：**支出はそのまま、収入に足す**。引き落とし予定と残高からは引く（7章）
- お店や通信料（楽天モバイル）で使ったポイントは記録しない（本人の決定）。楽天モバイルは、ポイント利用のあとの残りだけをカードに請求し、利用明細にもポイント分は載らない（楽天モバイルの公式ページ・10/7）。お店でポイント＋カードのときも、カードには残りだけ請求されるので、アプリの支出（カードで払った分）は手元から出たお金と合う

## 4. メールの取り込み（F-01〜F-03）

### 4.1 流れ

1. 1時間おきに動く（時間主導トリガー）
2. Gmail API（読み取り専用）で次の条件のメールの番号を集める（10/6 に実際の検索で2通とも出ることを確認）
   `from:info@mail.rakuten-card.co.jp カード利用のお知らせ newer_than:60d -in:spam`（`includeSpamTrash: true`）
   - **ゴミ箱のメールも読む**（10/6 本人）。本人は届いたメールをすぐゴミ箱に入れることがあり、1時間おきの取り込みの前に消すと取り込まれなかったため（Gmail のゴミ箱は30日で空になる）
   - **迷惑メールは読まない**（`-in:spam`）。楽天カードを名乗る偽のメールを取り込まないため
3. もう取引のシートにある番号は飛ばす（F-02）。新しいものだけ本文（text/plain）を取りにいき、下の規則で分解する。**本人があとでメールを消しても、記録はシートに残る**
4. 速報 → 確定 の順になるよう、メールの届いた順に並べてから突き合わせる
5. 変えた行はその行だけ、新しい行は末尾に書く。シートを丸ごと書き直さないのは、同じ時間に API 側が別の行を変えていても消さないため
6. 記録（3.7）に1行残し、設定の `最終取り込み` を書き換える

本文の文字コード：メールは ISO-2022-JP で届くが、Gmail API は UTF-8 に直して返すと報告されている（[gogcli #446](https://github.com/openclaw/gogcli/issues/446) など。公式の文書では未確認）。まず UTF-8 で読み、化けていたらメールに書いてある文字コードで読み直す。

1回の処理は数秒の見込みなので、1日24回動いても無料枠（合計90分/日）に収まる。

### 4.2 メールの見分け方と分解 ✅（実物2通で確認・10/6）

| 種類 | 件名 | 本文の形 |
|---|---|---|
| 速報版 | `【速報版】カード利用のお知らせ(本人ご利用分)` | `■利用日: 2026/10/01` `■利用者: 本人` `■利用金額: 2,000 円` が1組 |
| 確定版 | `カード利用のお知らせ(本人ご利用分)` | `■利用日:` `■利用先:` `■利用者:` `■支払方法:` `■利用金額:` `■支払月:` の組が**1つ以上**続く |

- 本文を `■利用日:` で区切って、1組ずつ取り出す
- 金額は `1,234 円` からカンマと「円」を除いて整数にする
- 決まった形に合わないメールは取り込まずに、記録（3.7）に「読めなかった」と残す。次の回にもう一度試す。3回失敗したら試すのをやめて、設定の `読めなかったメール` に載せ、ホームの「やること」に出す
- ⚠️ 確認できた実物は2通だけ。キャッシング・分割払い・家族カードなど、ほかの形のメールは見ていない

### 4.3 速報と確定の突き合わせ（F-03）

1. 確定版の1件が来たら、**同じ利用日・同じ金額で、まだ置き換えていない速報**を探す
2. 見つかったら、その速報の行を確定の内容で上書きする（状態＝確定、利用先・支払月を入れる、対応する速報に元の id）
3. 見つからなければ、新しい行として足す
4. 同じ条件の速報が2つ以上あれば、古いほうから使う
5. **確定にならないまま14日たった速報**（✅ 10/6）は、ホームの「やること」に「確認が必要な速報が◯件」と出す。キャンセルや、確定で金額が変わった可能性があるため。本人がそこで消すか、確定の1件と結びつける
6. **CSV（S-09）から先に足した行**（出どころ＝CSV・状態＝確定）と同じ利用日・同じ金額のメールが来たら、二重にしない（10/6）
   - 確定版：その行をメールの行にする（id をメールのもの、出どころ＝メール、利用先・支払月をメールの内容に）。id がメールのものになるので、次からそのメールは読みにいかない。個別に決めたカテゴリは残す
   - 速報：その行の「対応する速報」に入れて結びつけるだけ

### 4.3.1 e-NAVI の CSV（S-09）✅（本物1つで確認・10/6）

- パソコン版 e-NAVI の「ご利用明細」からダウンロード（ファイル名の例 `enavi202610(****).csv`）。UTF-8（BOM つき）、全部の欄が `""` で囲まれている
- **形が2つある**（10/6 に本物9つで確認）。下の列は、いちばん新しい明細の形（A）。前の月の確定済みの明細（B）は「支払月」の列がなく、8列目が `7月支払金額`（6月払いからは `当月請求額` の列が増える）。最後に `新規サイン`。B の店名は前に何も付かず、海外の利用は後ろに `利用国USA` が付き、次の行に日付のない「現地利用額…変換レート…」が来る
- どちらも途中に空の行があり、`■ご利用キャンセルなど` の見出しのあとにキャンセル・返金の行が続く（金額はプラス）。元の利用と同じ金額とは限らない（一部の返金など）ので、**足さずに合計だけ出す**。利用の合計 − キャンセルなど は、e-NAVI の一覧の支払金額と8か月中6か月で一致した（2月・4月払いだけ CSV のほうが多い。理由は CSV からは分からない。ポイントでの支払いなどかもしれない）
- 照合の画面には、明細の利用の合計・シートのその月の支払い分の合計（同じなら「そろっています」）・キャンセルなど・差し引いた支払金額を出す（10/6 本人）
- 列：`利用日`（2026/09/28）・`利用店名・商品名`・`利用者`・`支払方法`・`利用金額`・`手数料/利息`・`支払総額`・`支払月`（「10月」か「11月以降」）・`10月支払金額`・`当月請求額`・`11月繰越残高`・`11月以降請求額`。月の数字が入った列名は、位置で読む
- 店名は、メールの利用先の前に `マスター国内利用　MZZ ` や `海外利用　１　` が付いた形（10/6 に同じ利用の CSV とメールで確認）。前の言葉を外し、NFKC で全角・半角をそろえる（メールの取り込みと同じ）
- その月の支払い分（支払月＝「10月」）だけを照らし合わせて足す。支払いの年は、その月の分のいちばん新しい利用日から決める（12月の利用 → 翌年1月払い）
- 照らし合わせ：利用日と金額が同じなら同じ利用。同じ日・同じ金額が複数あれば、店名が同じものを先に使う。シート側はメール・CSV から入った支出（取消・手入力・収入は除く。支払月は問わない）
- 結果：一致／CSV にだけある（足す候補）／メールにだけある（シートで支払月がその月なのに CSV に出てこない＝キャンセルかも）
- ⚠️ 確認できた CSV は本人の1回払いだけ。分割払い・リボ・家族カードの行の形は見ていない（本人以外とマイナスの行は読まない）

### 4.5 楽天証券の積立（積立NISA）✅（実物のメールで確認・10/7）

10/7 本人：毎月の積立NISA も固定費に入れたい。数える場所は**支出として全部**（固定費・今月の支出・予算・統計）。カードではないので、引き落とし（3.1.1）と CSV の照合（4.3.1）には入れない。

## 5. API と安全面（N-02）

### 5.1 API の形

- GAS ②（API）を **ウェブアプリ** として公開する。Gmail の権限は持たせない（1.1）。アクセスできる人は「全員」。PWA から呼ぶには、ログインなしで届く必要があるため（出典：[Content Service](https://developers.google.com/apps-script/guides/content)）
- 呼び出しは**全部 POST 1本**にまとめる。本文は JSON の文字列で、送るときの種類は `text/plain`。`application/json` で送ると、ブラウザが事前の確認（preflight）をするが、GAS はそれに答えられないため（出典：[GreenFlux Blog](https://blog.greenflux.us/so-you-want-to-send-json-to-a-google-apps-script-web-app/)）
- 返ってくる中身は JSON。GAS は返事を一時的な URL に転送（リダイレクト）するので、それを追いかける設定にする（同上 Content Service）

```json
// 送るもの
{ "key": "（合言葉）", "action": "getData", "params": { "from": "2025-10", "to": "2026-10" } }
// 返るもの
{ "ok": true, "data": { ... } }   // 失敗はすべて { "ok": false }

// 書き込みのときは fresh に getData と同じ期間を付けて送る（10/7）
{ "key": "…", "action": "saveDetail", "params": { ... }, "fresh": { "from": "2000-01", "to": "2027-12" } }
// → 書いたあとの getData の中身が、同じ返事の fresh に入って返る（取り直しの通信が1回減る）
{ "ok": true, "data": { "id": "…" }, "fresh": { "transactions": [ ... ], ... } }
```

- **書き込みの速さ（10/7 本人「保存してから反映されるまでが長い」）**：GAS への通信は1回ごとに時間がかかるので、回数を減らす
  - fresh：書き込みの返事に新しいデータを入れて返す。前は「書く → 取り直す」で2回だった。fresh を作るのに失敗しても、書き込みは成功として返す（PWA が別に取り直す）
  - saveDetail：利用の詳細の保存（カテゴリ・名前・「いつもこの内容」）を1回にまとめる。前は最大3回（対応表 → この行 → 取り直し）
  - PWA は、保存を押したら返事を待たずに画面を先に変える（下の 5.1.1）

|---|---|---|

| setRule | 対応表に足す・変える（F-06）。同じ利用先の行のうち「個別」以外（未分類・対応表）にまとめて当てる。4.4 の4 より広げた（10/6。対応表を変えたら、前の対応表で付いた行も変わるほうが自然なため） | ① |
| addPointPayment | カードの請求をポイントで払った記録を足す（F-38・10/7）。`{ date, amount: 1〜1,000万の整数 }`。種類＝収入・状態＝ポイント払い・支払月＝date の月・名前＝ポイント（3.1.2）。消すときは deleteManual | ③ |
| addIncome | 収入を手で足す（F-31）。`{ date, amount: 1〜1億の整数, memo（名前） }`。種類＝収入・状態＝手入力・カテゴリなし。収入の行には setCategory を断り、setRule でもカテゴリを当てない | ③ |

#### 5.1.1 PWA の保存のしかた（10/7）

- **先に画面へ出す**：利用の詳細と振り分けの保存は、押したらすぐシートを閉じて（振り分けは次の1件へ進んで）画面を変え、裏で送る。画面に出すデータ＝サーバーから最後に取れたデータ＋返事を待っている保存（pending）。新しいデータが届いたときも、返事を待っている保存は当て直す
- **待っているあいだ**：画面の下に「ぐるぐる＋保存しています…」。続けて保存したら全部終わるまで出し、最後に「✓ 保存しました」（2件からは「✓ 2件 保存しました」）。失敗したら、その保存を外して画面を元に戻し、「…（元に戻しました）」と赤で出す
- **返事を待つ保存**（手入力・予算・資産・CSV・削除）：押した直後にボタンの中を「ぐるぐる＋保存しています…」にして押せなくする。失敗したら、入れた中身を残したまま押せるように戻す
- **書き込みは1つずつ順に送る**：返事の新しいデータが、古いものに戻らないように。取り直しも、あとから送ったものの返事を先に使っていたら、前に送ったものの返事は捨てる

集計（今月の合計、先月の同じ日まで、支出トップ、グラフ）は**PWA 側で計算する**。データは月に数十〜百件ほどの見込みなので、まとめて渡しても軽い。

### 5.2 合言葉の仕組み

- 合言葉は GAS ② の `makeKey` が作る**64文字のランダムな文字列**（UUID 2つ分）。スクリプト プロパティには**ハッシュ（SHA-256）だけ**を置き、合言葉そのものは保存しない。コード、リポジトリ、URL には書かない
- PWA では最初の1回だけ入力し（S-00）、端末の中に保存する
- **URL のクエリ（`?key=…`）には載せない**。URL は履歴やログに残りやすいため。POST の本文で送る
- 合言葉が違うとき、なかったときは、どちらも同じ `{ "ok": false }` だけ返す。違いからヒントを与えないため
- 間違いが1時間に10回に達したら、その後はすべて断る（GAS のキャッシュで数える）。⚠️ URL を知っている人がわざと間違え続けると、本人も締め出される。そのときはデプロイし直して URL を変える
- `doGet`（URL を開いただけのアクセス）はデータを一切返さない
- 合言葉を変えたいときは `makeKey` をもう一度実行して、端末で入れ直す

- `action` の名前は、手続きの一覧が**自分で持っている名前**だけを受け付ける（`__proto__` や `constructor` のような、JavaScript のオブジェクトが元から持っている名前で中に入られないように）
- 文字の入力（メモ・利用先）は長さを決め、`= + - @` で始まるものは断る（表計算の式として読まれないように）
- 中で失敗したときは、決まった文だけ返して、エラーの中身は返さない

### 5.3 想定する危険と対策

| 危険 | 対策 |
|---|---|
| API の URL が他人に知られる | 合言葉がなければ何も返さない。URL だけでは読めない |
| 合言葉を総当たりされる | 32文字以上＋1時間10回まで |
| 公開リポジトリから秘密が漏れる | 合言葉・シート ID・データは置かない。公開前にリポジトリ全体を検索して確かめる |
| iPhone をなくす | 端末に残るのは合言葉と、最後に取れたデータ。iPhone のロックに頼る。気づいたら合言葉を変えれば、その端末からは読めなくなる |
| メールの形が変わって読めなくなる | 読めないメールはラベルを付けずに残し、「やること」に出す（4.2） |

### 5.4 完成後に実際に試すこと（N-02）

「安全です」と言う前に、次を**実際にやってみて**結果を記録する。

1. 合言葉なしで POST する → `ok:false` だけが返るか
2. 間違った合言葉で POST する → 同じ返事か
3. 合言葉を URL のクエリに付けて GET する → データが出ないか
4. 11回間違えたあと、正しい合言葉でも1時間断られるか
5. 公開リポジトリ全体と、公開されたサイトのファイルを検索して、合言葉・シート ID・金額が入っていないか
6. ほかのサイトのページから API を呼んで、合言葉なしでは読めないか
7. 古い版の公開 URL が残っていて、そこから読めないか

## 6. PWA（web/）

- **ホーム画面に追加**：`manifest.webmanifest` にアプリ名・アイコン・色を書く。iPhone では Safari の共有メニューから追加する
- **アイコン**（10/7 本人が4案から選んだ：家計簿のノート＋金の ¥ コイン、紺の地）：iPhone 用（apple-touch-icon・180px）は四角のまま（角は iPhone が丸める。透明にすると黒く出る）、icon-192／512 は角を丸めたもの、maskable は絵を 80% に縮めて紺の地に置いたもの。アイコンを替えたら `?v=` を上げる
- **オフライン**：`sw.js` で画面のファイル（HTML・JS・CSS・写真）を端末に保存する。データは最後に取れたものを端末の保存場所（IndexedDB）に置き、開いたらまずそれを出して、裏で新しいデータを取りにいく（N-07）
- **iPhone と PC の両方**：画面の幅で並べ方を変える（2列・左メニュー。画面設計 4章）
- **グラフ**：棒グラフ・円グラフ・折れ線は、まずは自分で SVG で描く案。部品（ライブラリ）を使うかは見た目を詰めるときに決める ⬜
- ⚠️ iPhone のホーム画面に追加した PWA は、Safari とは保存場所が別になると言われている。合言葉は、ホーム画面から開いた状態で入れる（実機で確認する）
